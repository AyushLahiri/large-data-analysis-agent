# Cross-folder joins

## Start with the smallest useful join

- Decide what needs linking. Usually, joining whole datasets is unnecessary. If independent results answer the question, calculate each separately. If the results need combining, prefer joining the smaller summary tables on a logical variable.
- If only one folder is selected and the question needs another folder, tell the user to select the entire project so both are in scope.
- For example, calculate state-level statistics for one table and state-level statistics for the other. Use lean distinct-value and count checks to see if the states can be joined. The same state may be named differently in each table. If the evidence supports a mapping, recode the names or codes in code. Check for collisions, coverage, and duplicate keys after recoding, then join on state. If you cannot establish a reliable mapping, leave the results separate. Calculate any further columns that depend on both tables after the join.
- Review the project’s saved join rules and notes from previous sessions. Use them when they apply to these folders, this question, and the records or groups being joined.

## Discover and check record keys

- If a record-level join is needed, identify the reported primary key or candidate row key in each folder. Confirm separately that every row has a nonmissing key and each key occurs once. A folder’s own row key and the key used to link folders can differ.
- The schema marks the loader’s generated `ow_id` row key as synthetic. If either folder has a synthetic row key, you cannot directly join the datasets on their reported keys or by row order. Continue checking for source identifiers that can form a shared key, or consider a summary-level join.
- Run a few broad column or codebook searches separately in each folder. Take note of all available identifier fields. Look for names with ID, identification, line number, household number, region number, block number, and similar patterns. Check what each field identifies, then select the plausible keys or combinations to test.
- Profile every available identifier separately in each folder. Report total rows, nonmissing values, and the total number of distinct values. Show up to five distinct values that occur more than once, each with its frequency. Use the same checks for a candidate combination before joining. Keep diagnostics compact.

## Test the best key first

- Start with the most plausible join key. Join only the key columns first. Check for a perfect match by counting matched and unmatched rows on each side and identifying the keys present only in each folder. Determine whether the join is one-to-one or one-to-many. A repeated matchable key on the left makes that orientation invalid. Many-to-one, many-to-many, and cross joins are prohibited under all circumstances. For Python, require explicit `merge(validate='one_to_one')` or `merge(validate='one_to_many')` and exclude missing join keys from matching.
- If either side has unmatched rows, randomly sample 10 unmatched rows from each side with unmatched rows, or all of them if fewer than 10 exist. Surface all available keys and identifiers for those rows and no other columns in this first sample. Then use what you know about both datasets to infer the expected relationship and select up to five other columns that could explain the mismatches. For example, one dataset contains women and the other husbands. Unmatched women may be unmarried. If the random samples and selected columns support your explanation, run a final small aggregate count across all unmatched records to verify the pattern. Keep the samples out of the user-facing answer.
- If the tested key works and any unmatched records have a logical explanation, use the verified key. When that key is the primary key, use the primary key as the join key. Keep the unmatched counts and any coverage limits in the interpretation.
- If the first key fails, use your knowledge of the datasets to infer how other identifiers might combine or encode the same key. Rank the alternatives by plausibility and try up to eight different key iterations. If a plausible match requires a recode, implement the recode in code. Preserve meaningful padding and codes and check the transformed keys for ambiguity and collisions. Repeat the same uniqueness, match, cardinality, and unmatched checks for each candidate until a key is verified. Similar-looking values, equal counts, or row order are insufficient.
- If the question needs a record-level join and those checks find no defensible key, report the best candidate keys or combinations, their statistics, and why the join appears invalid. Ask the user for the specific mapping or key guidance needed. This is the exception to the general instruction to avoid user questions.

## Execute and record

- For three or more folders, combine them in pairwise steps. At each step check the actual left and right inputs again. A prior one-to-many join can change key uniqueness.
- If you work entirely in SQL, use CTEs. Put each projected or recoded input in its own named `q_…` CTE and join those CTEs explicitly on every verified key. Keep a separate CTE for each iterative step. If you sample unmatched keys in SQL, use a row number ordered by `random()` and filter it to the sample size. Return small diagnostics within the usual result limits.
- If you continue with analysis after a successful join, check what each joined row represents. If one household joins to four people, its electricity bill appears four times. A household-level average must still count that household once. Account for this in the analysis and interpretation, and tell the user how you handled it.
- If a join is confirmed by executed checks, on finish set `join_success` to `yes`, provide the participating folder IDs in `join_folders`, and fill `join_rules_discovered` with up to 10 bullets of at most 30 words each. Record what was joined, how it was joined, any preprocessing or recodes required, the join rules discovered, and the expected join behavior, including cardinality and coverage. These notes are saved in Atlas at the project level and loaded with the skill in later sessions. Leave the join fields empty or `no` until a join is confirmed.
